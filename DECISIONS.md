# Decisions

- **The harness replaces ken.** ken is reference material only: no runtime proxy, no ken process, no reads or writes of `~/.local/share/ken`. The harness owns the vault, MCP surface, mastery and state.
- **Bun install:** installed via the official installer to `~/.bun`; `bun`/`bunx` symlinked into `~/.local/bin` so package scripts work in bash and fish.
- **MCP endpoint:** SDK `WebStandardStreamableHTTPServerTransport` in stateless JSON mode, so it runs natively on Bun without the Node adapter.
- **UI build:** `bun run start` builds the UI only when `dist/ui/index.html` is missing; `HARNESS_SKIP_BUILD=1` and `HARNESS_FORCE_BUILD=1` override this.
- **SQLite:** M0 creates only a `meta` table; the real schema lands in M2/M3.
- **Config:** port 4747, host 127.0.0.1, LAN off by default, all overridable by env (`PORT`, `HOST`, `HARNESS_VAULT`, `HARNESS_DB`, `HARNESS_LAN`, `HARNESS_MCP_TOKEN`).
- **Design register:** product UI, restrained color, dark-first (night study on laptop/phone). One system sans, fixed rem scale, accent reserved for actions/selection/state. Impeccable loaded for token work; Lane C inherits these tokens instead of inventing a palette.
- **ken mapping:** see `docs/ken-mapping.md`. Vault layout follows SPEC (`courses/<code>/`); ken formats are borrowed where useful, but SPEC wins on any conflict.
- **Consolidated SPEC + DESIGN:** `SPEC.md` and `DESIGN.md` come from the student's Downloads; DESIGN wins on look/layout/behavior, SPEC wins everywhere else. Work is tracked as one milestone card at a time.
- **Name:** the app is **Hilum** (`package.json`, title, manifest); icons live in `public/`.
- **Tokens:** CSS `light-dark()` with a `data-theme` override; palette is H&E (primary #4338A8, accent #F08CB0). Contrast is tested, not eyeballed.
- **Reader prefs:** text size/leading are inline on the article wrapper; markdown must not set its own base font-size or leading.
- **MCP content surface:** `update_course` patches `courses/<code>/course.md` frontmatter (null clears) and is idempotent via `request_id`; notes are resources at `vault://<path>`.
- **Demo data:** screenshots use a fabricated vault under `/tmp/opencode/demo-vault`; never present it as course material, never commit it.
- **Questions live in SQLite.** The vault supplies notes and past papers; `questions` rows are the bank. `source_paper` and `cites` point back into the vault, so nothing is duplicated as markdown.
- **Import never auto-verifies.** `import_past_paper` forces `verified=false, unverified=true`, derives ids from course + paper + index, and rolls back the whole batch on any citation failure.
- **Verification is explicit.** `update_question` edits content only; only `verify_question` (or the UI action) flips `verified`/`unverified`.
- **Citation validation:** anchors may be explicit `{#id}` or heading slugs; quotes are compared whitespace-normalized inside that section. Banked items require at least one quoted cite.
- **Papers snapshot the bank.** `paper_items` stores question ids at build time; a paper is a stable set even if the bank is edited later.
- **Papers draw only verified questions.** Selection is restricted to `verified = 1 AND unverified = 0`; a shortfall fails the build instead of padding silently.
- **Scoring is deterministic and server-side.** TF uses `per_statement` by default (or `all_or_nothing`); MCQ can carry negative marks per section; spotter compares normalized text against `answer` plus `accepted`; theory always queues for grading.
- **Active attempt survives reload.** `eh-attempt` stores `{id, course}`; the app routes back to the runner and the timer is derived from the attempt's `started_at`, never from a client-side counter.
- **Spotter images are vault assets.** Paths resolve relative to the first cited note (or from `courses/`); remote/data URLs are rejected and the file must exist inside the vault.
- **Grades are separate from answers.** `answers.auto_score` holds the awarded total for every graded item; `grades` keeps the rubric breakdown, feedback, tags and grader so a re-grade can replace the explanation without losing the score history contract.
- **Theory is never auto-correct.** A graded theory item keeps `correct = null`; the debrief shows the grade and rubric instead of forcing a binary, while evidence uses the 50% threshold only for mastery input.
- **Rubric headings are validated by arithmetic, not by a fixed rubric schema.** A question's rubric is markdown; the grader returns headings with awarded/max, and the server enforces non-empty rows, per-row maxima and the question total. This works with draft rubrics.
- **Evidence is written when an answer becomes final.** Objective answers write evidence at submit; theory writes it at grade time. Re-grading deletes and rewrites that answer's rows, so evidence stays idempotent.
- **SSE is a single local stream.** One EventSource per app shell carries submitted/graded events; the server keeps no per-client state and drops a subscriber when the request aborts.
- **Photo answers live beside the database.** Uploads go to `dirname(db)/uploads` (or `HARNESS_UPLOADS`), not the vault, so student handwriting is not indexed as course material. Only image MIME types with a size cap are accepted, and filenames are attempt/question scoped.
- **The paper list shows the latest attempt.** Results opens the newest submitted attempt for that paper and Resume opens the newest in-progress one; full attempt history is available through the API for later screens.
- **Sessions are first-class, not exam attempts.** `sessions` holds the live teaching loop, `activities` holds each pushed spec/response, and `agent_requests` holds Ask-the-agent messages. Exam attempts stay in `attempts`; the two only meet through evidence.
- **One ActivitySpec catalog.** The server parses every spec with Zod, then checks the semantic rules (cloze blanks, MCQ key, compare-table row width). Unknown component types are rejected before write with the available list, so an agent can self-correct without a round trip through the UI.
- **Every pushed activity is cited.** `validateCites` runs before insert; a bad note, anchor or quote writes nothing. Banking is stricter: at least one cite must carry a quote.
- **Live answers are validated server-side.** The renderer's disabled state and "Still needed" labels are a convenience; `SessionService.respond` rejects a missing MCQ/TF/cloze answer, an out-of-range option, or a too-short think-aloud.
- **Student actions do not forge agent presence.** `agent_seen_at` is touched only by session MCP tools. Reading a session, starting one from the app, answering an activity or banking from the UI never makes the status strip claim an agent is connected. The connected window is 3 minutes so a slow free model does not flicker into "not connected" mid-thought.
- **The long poll is bounded.** `await_response` waits up to 25 s in 400 ms steps, returns one unseen response at a time, and includes open requests and newly seen render errors. Render errors are marked seen so a broken diagram cannot trap the loop forever.
- **The session note is a normal vault note.** Ending writes frontmatter (session id, course, goal, duration, counts) plus the summary and activity log; ending twice returns the existing session rather than overwriting the note.
- **Mermaid is local and lazy.** `mermaid` loads through a dynamic import only when a diagram is present; strict security is on, parse failures are reported to the agent, and the SVG follows the active light/dark theme.
- **Banked activities are vault files for now.** The v1 path stores the spec and citations in `courses/<code>/activities/`; replay, offline scheduling and paper inclusion remain future work after mastery lands.
